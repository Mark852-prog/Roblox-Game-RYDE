# Architecture

How the project is organised and why. Updated every milestone.

## Workflow

```
src/            Luau source code (the real game code)
assets/         Generated binary models (TestTrack.rbxm)
tools/          Build scripts (map generator, build.sh)
tests/          Automated tests, run with Lune outside Roblox
build/RYDE.rbxl The finished place file you open in Roblox Studio
```

- **Rojo** (`default.project.json`) maps the `src/` folders into the Roblox
  game tree and builds `build/RYDE.rbxl`. The same project file can later be
  used with `rojo serve` + the Rojo Studio plugin for live syncing.
- **Lune** (a standalone Luau runtime) generates the test map
  (`tools/build-testtrack.luau`) and runs the unit tests.
- **Selene** lints the game code. `roblox_lite.yml` is an offline standard
  library (the full one needs a download that isn't available in every environment).
- `tools/build.sh` does all of the above in order.

The map is generated by a script, not placed by hand, so it is reproducible,
reviewable as text, and easy to adjust. Later districts may be built in
Studio and exported to `assets/` as `.rbxm` files.

## Where code lives in the game

| Folder in repo | In the game | Runs on | Purpose |
|---|---|---|---|
| `src/shared` | `ReplicatedStorage.Shared` | both | Configs, unit conversion, validation, shared maths |
| `src/server` | `ServerScriptService.Server` | server | Authoritative game logic |
| `src/client` | `StarterPlayer.StarterPlayerScripts.Client` | each player | Input, camera, UI, visual effects |

One entry script per side (`Main.server.luau`, `Main.client.luau`) starts
everything else, so start-up order is explicit and there are no stray scripts.

## Key decisions

### 1. Scale and gravity — 1 stud = 0.35 m, gravity = 28.03 studs/s²

The default R15 character is ~5 studs tall; at 0.35 m/stud that is 1.75 m,
so bikes built to real dimensions look right next to the rider.
Roblox's default gravity (196.2) is about 7× real gravity at this scale,
which would make jumps tiny, short hops. We use real gravity
(9.81 m/s² ÷ 0.35 = 28.03 studs/s²) so jumps, landings and wheelies behave
plausibly. Character jump height is set to 4 studs (a bit "gamey" but feels
fine). All vehicle configs use real-world units (kg, m, N, km/h) and are
converted by `Units`. The server warns at start-up if `Workspace.Gravity`
was changed.

### 2. Vehicle configs are data, validated at start-up

Each vehicle is one file in `Config/Vehicles/` listed in `VehicleCatalog`.
`VehicleSchema.validate` checks every field's presence and range plus
cross-field rules (centre of mass inside the wheelbase, damage threshold
order, …). The server prints problems to Output at start-up and the tests
fail on them, so tuning mistakes are caught immediately.

### 3. Surfaces are looked up by material name

`SurfaceConfig` maps Roblox material names (works for both Parts and
Terrain) to grip, rolling resistance, roughness and an effect family.
Any Part can override its material with a `Surface` attribute (e.g. a
plastic part that should behave like ice).

### 4. Streaming is off for now

`Workspace.StreamingEnabled = false` keeps early client code simple (every
part exists on every client). It will be revisited when the open-world map
grows (Milestone 5/9); systems will be written to tolerate streaming.

### 5. Planned vehicle physics (Milestone 2–3) — for review

Not implemented yet. The plan, so you can see where this is going:

- **One physics body per bike.** An invisible chassis part carries the
  bike's tuned mass. Visual parts and wheels are massless and non-colliding.
- **Raycast wheels and suspension** instead of Roblox's wheel/spring
  constraints. Each wheel casts a ray down; a spring-damper force (tuned by
  natural frequency and damping ratio, so it doesn't depend on mass units)
  is applied at the contact point. This is far more stable for two-wheelers
  than constraint wheels, which tend to jitter and tip over.
- **Forces at the contact patches.** Drive force at the rear contact,
  braking at each contact, lateral tyre grip limited by load × surface grip.
  Because the drive force acts below the centre of mass, **wheelies and
  stoppies emerge from the physics** (weight transfer), and the rider's
  fore/aft weight shift (an input) moves the balance point.
- **Balance and leaning.** A real rider balances a bike constantly; we model
  that with a roll controller that targets the physically correct lean
  angle for the current speed and turn rate (atan(v·ω/g)). In the air the
  controller is off and the rider only has limited pitch/roll input — no
  auto-levelling.
- **Network ownership.** The server gives physics ownership of a bike to
  its rider, so controls feel instant. The server stays authoritative for
  who may ride which bike, damage, crashes, rewards and police; it also
  sanity-checks speed and position to limit exploits. Trade-off: a
  modified client could still alter its own bike's motion within those
  limits — that's the standard Roblox compromise for responsive vehicles.

## Server vs client responsibilities (current)

| Component | Side | Authoritative? |
|---|---|---|
| Startup checks (`Main.server`) | Server | Yes — publishes `RYDEServerHealthy` attribute |
| Debug HUD (`UI/DebugHud`) | Client | No — display only |
| Configs (`Config/*`) | Shared | Read-only data; the server's copy is the one that counts |
